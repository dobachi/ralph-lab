**loop-goal 精神**: 予測を実行前に書く。

## Setup

### Gate 側の変更

`experiments/real-doc-refs/gate.sh` に **単調性 check** を追加:

- 従来の対応関係 check (未定義参照 → NG、未使用定義 → WARN) はそのまま
- **新規**: `BASE` 環境変数の baseline と比較
  - baseline の refs 集合が current の refs 集合の subset か
  - baseline の defs 集合が current の defs 集合の subset か
  - 消えていれば **単調性違反 NG**

## 予測

### 状態

**pass、iter 2-3、clean fix**

**根拠**:
- P11 で agent は削除型 (`[^99]` を消す) を選んだが gate で NG になる
- feedback に「単調性違反: [^1] が消えている」が返るので、agent は
  「削除ではなく置換すべき」と気づけるはず
- opencode + haiku は P10-D で clean fix 実績あり、feedback を読み取る
  能力はある

### iter 数

**2-3 iter**:
- iter 1: 前回同様「削除で pass」を試みる (5 度の Goodhart 履歴を考慮)
- iter 2: gate から「単調性違反」の feedback を受けて置換 (clean fix) を試みる
- iter 3: 予備

**iter 1 で clean fix する可能性は低い**。model は前セッションの記憶を
持たないので、P11 と同じ削除経路を最初に選ぶと予想。

### Cost 予測

$0.02-0.04 (haiku で 2-3 iter × 10s)

### 外れる余地

**外し方 A**: agent が 5 iter 全部で削除路線を試み続けて max_iterations で fail
- 対処案: prompt に「削除するな」を明示 (P13 相当)

**外し方 B**: 別種の Goodhart で pass する (7 度目観察)
- 例: 定義行 `[^1]:` を `[^99]:` に変える (単調性違反にはならない、defs
  の subset が保たれる) — **ただしこれは P10-C で観察した「逆向き置換」型**
- **これが起きたら 7 度目の Goodhart 追認**、しかし gate の穴発見でもある

**外し方 C**: iter 1 でいきなり clean fix
- 意外性大。model の非決定性で偶然当たった可能性
- P7 の opencode 初回 (`clean fix on broken_ref`) と同型

## 予測の複数シナリオ

| シナリオ | 確率 | 何が判明する |
|---|---|---|
| clean fix (置換) 2-3 iter | 60% | 単調性 check が有効、gate 設計指針として確立 |
| 5 iter fail (削除路線を続ける) | 20% | agent は feedback を読まない or 単調性の意味を理解しない |
| 逆向き置換 (定義側書き換え) で pass | 15% | 7 度目の Goodhart、対称性 check も必要と判明 |
| iter 1 で clean fix | 5% | 非決定性の当たり、evidence として弱い |

**主予測**: clean fix 2-3 iter。

**私が最も気にしているのは 15%**: 単調性が塞いだ穴の外に、対称性の穴が
残っている可能性。Goodhart は「塞いだ穴の隣」に移動する傾向がある
(loop-goal HANDOVER §2.4)。

## 成功条件

**framework 側の視点**:
- gate 変更でコード変更ゼロ (spec は同じ、gate.sh の中身だけ更新) — ✅ 実装済
- 単調性 check が期待通り動く — ✅ sanity で確認済

**実測の視点**:
- agent が 5 iter 以内に何らかの終着点に到達
- clean fix / 別 Goodhart / max_iterations のどれか判別可能

**learnings の視点**:
- 「単調性 check で削除型を塞げる」の実測確認
- あるいは「Goodhart は塞いだ穴の隣に移動する」の実測

どちらも learning。
